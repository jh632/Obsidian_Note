### 二、延迟创建的任务（运行时按需创建）

这些任务在启动时不创建，收到服务器命令后动态创建。它们的栈从内部堆（DRAM）分配，但 PSRAM 已配置为允许栈放在外部内存。

| 任务名         | 栈(words)  | 栈(bytes)   | 优先级 | 触发条件                               |
| -------------- | :--------: | :---------: | :----: | -------------------------------------- |
| `ws_fast`      | **6144**   | **24,576**  | 8      | START_COLLECT → `ws_data_push_start()` |
| `ws_env`       | 4096       | 16,384      | 8      | START_COLLECT → `ws_data_push_start()` |
| `PPG_TASK`     | 4096       | 16,384      | 8      | START_COLLECT (mask 0x01)              |
| `EDA_TASK`     | 4096       | 16,384      | 8      | START_COLLECT (mask 0x02)              |
| `IMU_TASK`     | 4096       | 16,384      | 8      | START_COLLECT (mask 0x04)              |
| `posture_TASK` | 4096       | 16,384      | 8      | START_COLLECT (mask 0x08)              |

### 四、内存占用汇总

#### 启动时总保留栈空间

```
应用层任务:    24,576 words =  98,304 B  (6 个任务)
IDF 内部任务: ~33,644 words = 137,576 B  (~12 个任务)
─────────────────────────────────────────
启动时总计:   ~58,220 words = 235,880 B
```

#### 延迟创建总保留栈空间

```
数据采集 (4个):   16,384 words =  65,536 B  (PPG+EDA+IMU+posture)
WS 推送 (2个):    10,240 words =  40,960 B  (ws_fast + ws_env)
OTA (1个):        12,288 words =  49,152 B
─────────────────────────────────────────
延迟总计:         40,912 words = 163,648 B
```

### 五、关键发现

1. **栈消耗不是 heap 消耗的全部**
   - 栈保留空间不代表立即从 heap 分配 — 部分任务使用静态分配（如 BLE Controller 的 `TASK_DESC_*` 符号在 map 中可见，表明静态 TCB）
   - 但大多数 `xTaskCreate` 动态分配栈 + TCB，启动时确实消耗了~180 KB heap

2. **最大栈需求者**
   ```
   3. ws_ota_task  12,288 words = 49,152 B  ⭐← OTA 下载缓冲区
   4. ws_fast      6,144 words = 24,576 B   ← WS 推送任务
   5. gh3220_proc  4,096 words = 16,384 B   ← PPG 算法处理
   6. NimBLE host  4,096 words = 16,384 B   ← BLE 主机栈
   ```
   **ws_ota_task** 是栈最大的任务 — 12,288 words，但只在 OTA 期间短暂存在。

7. **优先级分布**
   - **最高优先级 (15)**: `gh3220_proc`, `MAX30009_task` — 传感器实时处理
   - **高优先级 (8)**: 所有 WS 推送 + 数据采集延迟任务
   - **中优先级 (6)**: `MPU_Task`, `env_sensors_task`
   - **中等 (4)**: `wear_status_task`
   - **低 (3)**: `ui_runtime`
   - IDF 系统任务优先级 18-24 比所有应用任务都高

4. **核心绑定**
   - 唯一 pinned 到 **core 1** 的任务: `MAX30009_task` (priority 15)
   - BLE Controller / NimBLE host 都 pinned 到 **core 0**
   - WiFi 驱动也 pinned 到 **core 0**
   - **core 0 负荷最重** — 承载 WiFi + BLE + 大部分 IDF 系统任务
   - **core 1 相对空闲** — 仅 MAX30009 + 可能的非绑定应用任务

5. **启动后只剩 12 KB heap 的后果**
   - 无法创建 `ws_fast` (需要 24 KB) 和 `ws_env` (需要 16 KB) 如果不使用 PSRAM
   - 实际上 `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=y` 意味着延迟任务的栈可以从 PSRAM 分配 — 这就是为什么设计上 WS 推送和 OTA 任务在启动时不创建
   - **如果 PSRAM 不可用**，12 KB heap 连一个延迟任务都创建不了

6. **优化空间**
   - `gh3220_proc` 和 `MAX30009_task` 都 priority 15，如果不同时运行高负载操作，可以降低
   - 延迟任务的标准 4096 栈可能偏大 — 可以考虑测量 high water mark 后裁剪
   - `ws_fast` 的 6144 栈是数据推送的核心瓶颈，需要运行时确认实际使用量

### 六、建议的运行时确认

在 `app_main` 结束时（heap 最低点）添加：

```c
// 列出所有任务及其高水位
TaskStatus_t *pxTaskStatusArray;
UBaseType_t uxArraySize = uxTaskGetNumberOfTasks();
pxTaskStatusArray = malloc(uxArraySize * sizeof(TaskStatus_t));
uxArraySize = uxTaskGetSystemState(pxTaskStatusArray, uxArraySize, NULL);
for (int i = 0; i < uxArraySize; i++) {
    ESP_LOGI("TASK", "%-20s stack=%5u free=%5u prio=%u core=%d",
             pxTaskStatusArray[i].pcTaskName,
             pxTaskStatusArray[i].usStackHighWaterMark,
             pxTaskStatusArray[i].uxCurrentPriority,
             pxTaskStatusArray[i].xCoreID);
}
free(pxTaskStatusArray);
```

这样可以获得每个任务的 **实际栈使用高水位**，判断哪些任务可以裁剪栈大小。
