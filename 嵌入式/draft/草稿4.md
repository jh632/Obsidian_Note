## WS 侧 req_id 分析

### 来源 A：设备端自增计数器

`wifi_ws_protocol.c:11`

```c
static uint32_t s_req_id = 0;
```

每次调用 `next_req_id()` → `++s_req_id`，自然回绕。

**谁用它**（设备主动发起的请求）：

| 入口                | 触发时机                               | JSON 示例                           |
| ------------------- | -------------------------------------- | ----------------------------------- |
| `encode_register()` | WS 刚连上，`WEBSOCKET_EVENT_CONNECTED` | `{"cmd":"register","req_id":1,...}` |
| `encode_ping()`     | `ping_timer_callback` 每 30s           | `{"cmd":"ping","req_id":17,...}`    |

两者走同一路径：

```
build_request_json()
  └─ cJSON_AddNumberToObject(root, "req_id", next_req_id())
```

---

### 来源 B：服务端下发的 req_id — 原样回传

设备收到的 type=command 消息自带 req_id。`parse_command`（第 180-186 行）**强制要求**该字段必须存在，否则拒绝处理。

接收后，所有 `handle_*` 函数通过 `ws_send_resp()` 原样回传：

```
ws_send_resp(cmd_name, cmd->req_id, code, data_json)
  └─ encode_resp(buf, buf_len, &written, cmd_name, req_id, code, data_json)
       └─ build_resp_json()
            └─ cJSON_AddNumberToObject(root, "req_id", req_id)  // 服务端的原值
```

**覆盖全部 6 个命令**：`sync_time`、`get_device_status`、`start_collect`、`stop_collect`、`shutdown`、`start_ota`。

---

### 谁没有 req_id

**数据推送不携带 req_id**。`encode_data()` 生成的 JSON 仅含 `device_id` + `type` + `timestamp` + 传感器数据字段，没有 `req_id`。

即每 200ms 发出的 PPG/EDA/IMU 三包数据，服务端只能靠 `type`+`timestamp` 区分，无法通过 req_id 做乱序检测或去重。

---

### 一句话流向

```
服务端下发命令 ──→ parse_command 提取 req_id ──→ handle_* ──→ encode_resp 原值回传
                                                      ↑
设备主动请求（register/ping） ──→ next_req_id() 自增 ──→ build_request_json 写入新 req_id
```
