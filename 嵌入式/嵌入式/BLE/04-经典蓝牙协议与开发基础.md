# 经典蓝牙协议与开发基础

> 经典蓝牙的正式名称是 **Bluetooth BR/EDR**：BR 表示 Basic Rate，EDR 表示 Enhanced Data Rate。它主要服务于持续数据传输和音频通信，常见用途包括耳机、键盘、手柄、串口设备和网络共享。
>
> 本文记录 Bluetooth Classic 的通用通信模型，并以 ESP-IDF 的双模设备为例说明开发入口。芯片是否支持 BR/EDR，需要以对应型号的数据手册和 SDK 版本为准。

## 1. 经典蓝牙与 BLE 的边界

| 项目 | 经典蓝牙 BR/EDR | BLE |
|---|---|---|
| 主要目标 | 连续数据、音频、输入设备 | 低功耗传感器和短消息 |
| 无线电信道 | 79 个 1 MHz 信道 | 40 个 2 MHz 信道 |
| 跳频 | 自适应跳频 AFH | 连接事件之间切换数据信道 |
| 基本速率 | BR 约 1 Mbps，EDR 约 2 或 3 Mbps | 1M、2M 或 Coded PHY |
| 连接组织 | Piconet、Scatternet | Central、Peripheral、Observer、Broadcaster |
| 数据模型 | L2CAP、SDP、RFCOMM、Profile | ATT、GATT、GAP、SMP |
| 常见 Profile | A2DP、HFP、HID、SPP、PAN | GATT Service、Characteristic |
| ESP-IDF Host | Bluedroid | Bluedroid 或 NimBLE |

NimBLE 是 BLE Host 的实现，不能用来建立 BR/EDR 链路。需要经典蓝牙时，应用需要使用支持 BR/EDR 的 Controller 和对应的 Host/Profile 实现。

## 2. 无线电与链路基础

### 2.1 频段与时隙

经典蓝牙使用 2.4 GHz ISM 频段，将频段划分为 79 个信道，信道间隔为 1 MHz。设备使用伪随机序列进行跳频，每个时隙长度为 **625 μs**，跳频速率为每秒 1600 次。一个 ACL 数据包可以占用 1、3 或 5 个连续时隙，发送完成后由链路另一端在后续时隙响应。

~~~text
2.402 GHz                                                     2.480 GHz
   │  ch 0   ch 1   ch 2                         ...    ch 78  │
   └────┬─────┬─────┬────────────────────────────────────┬─────┘
        └────────────── 1 MHz 信道间隔 ────────────────────────┘

时隙: | 625 μs | 625 μs | 625 μs | 625 μs |
      Central  →  Peripheral → Central  →  Peripheral
~~~

### 2.2 BR、EDR 与 AFH

- **BR** 使用 GFSK，空中原始速率约为 1 Mbps。
- **EDR** 在部分数据包中使用 π/4-DQPSK 或 8DPSK，空中原始速率约为 2 或 3 Mbps。
- **AFH（Adaptive Frequency Hopping）** 根据干扰情况减少受影响的信道，通信双方需要维护相同的信道映射。
- 速率数字表示无线电链路的原始速率，应用可得到的吞吐量还会受到包头、确认、Profile、Host 调度和 Controller 缓冲区影响。

## 3. Host 与 Controller 分层

经典蓝牙的 Host 与 Controller 通过 **HCI（Host Controller Interface）** 连接。HCI 可以是芯片内部的软件接口，也可以是 UART、USB 或其他物理接口。

~~~text
┌────────────────────────────────────────────────────┐
│ Application                                         │
│ A2DP / HFP / HID / SPP / PAN 等 Profile             │
├────────────────────────────────────────────────────┤
│ SDP                                                 │
│ 查询设备提供的服务记录和协议参数                    │
├────────────────────────────────────────────────────┤
│ RFCOMM                                              │
│ 在 L2CAP 上提供串口仿真和多路逻辑串口                │
├────────────────────────────────────────────────────┤
│ L2CAP                                               │
│ 信道复用、分段、重组和流量控制                      │
├────────────────────────────────────────────────────┤
│ HCI                                                 │
│ Host 与 Controller 的命令、事件和数据边界            │
├────────────────────────────────────────────────────┤
│ Controller                                          │
│ Link Manager / Baseband / Link Controller / PHY     │
└────────────────────────────────────────────────────┘
~~~

### 3.1 Controller 负责什么

Controller 负责射频收发、时隙安排、跳频、链路确认、重传、链路状态机以及部分链路安全过程。它通过 HCI 接受 Host 命令，并通过 HCI 发送 Command Complete、事件和 ACL 数据。

### 3.2 Host 负责什么

Host 维护设备发现、配对、服务发现、L2CAP 信道和 Profile 状态。应用通常通过 Profile API 访问 Host，只有调试底层问题时才需要直接查看 HCI 命令和事件。

## 4. Piconet 与设备角色

一个经典蓝牙 **Piconet** 由一个 Central 设备协调时隙和跳频序列，最多可以同时保持 7 个 Active Peripheral。设备可以在多个 Piconet 之间切换，形成 Scatternet；实际可用规模受到 Controller、Host 和调度能力限制。

~~~text
                         ┌──────────────┐
                         │   Central    │
                         │  手机或电脑   │
                         └──────┬───────┘
                ┌───────────────┼───────────────┐
                │               │               │
        ┌───────▼──────┐ ┌──────▼───────┐ ┌─────▼────────┐
        │ Peripheral 1 │ │ Peripheral 2 │ │ Peripheral 3 │
        │ 耳机或手柄   │ │ 键盘或鼠标   │ │ 串口设备     │
        └──────────────┘ └──────────────┘ └───────────────┘
~~~

BD_ADDR 是设备的 48 位蓝牙地址。设备的 Class of Device 用于描述设备类别和主要能力，可帮助用户界面显示“音频设备”“电脑”“电话”等分类。

## 5. 发现、建链与服务发现

经典蓝牙的连接流程通常包含三个阶段：Inquiry 找到设备，Page 建立链路，SDP 找到服务。

~~~text
设备 A                                      设备 B
  │                                           │
  │──── Inquiry ────────────────────────────→│  查询附近设备
  │←─── Inquiry Response / FHS ──────────────│  返回 BD_ADDR、时钟信息和设备类别
  │                                           │
  │──── Page ───────────────────────────────→│  呼叫指定 BD_ADDR
  │←─── Page Response ───────────────────────│  Page Scan 响应
  │←─── FHS / 链路参数 ──────────────────────│  建立 ACL 链路
  │                                           │
  │──── SDP Service Search / Attribute ─────→│  查询服务记录
  │←─── Service Record / Protocol Data ──────│  返回 RFCOMM、A2DP 等参数
  │                                           │
  │──── Profile 建链和业务数据 ──────────────→│
~~~

### 5.1 Inquiry

Inquiry 用于发现附近处于可发现状态的设备。设备需要开启 Inquiry Scan 才能响应。响应内容通常包括 BD_ADDR、时钟信息和 Class of Device，设备名称可能需要后续通过 Remote Name Request 单独读取。

### 5.2 Page

Page 面向已经知道地址的设备。被呼叫设备需要开启 Page Scan。Page 成功后，双方协商链路参数并进入 Connected 状态；设备是否出现在系统的蓝牙列表中，不代表某个业务 Profile 已经建立。

### 5.3 SDP

**SDP（Service Discovery Protocol）** 保存和查询服务记录。服务记录可以说明服务 UUID、Profile 版本、L2CAP PSM、RFCOMM 通道号以及其他连接参数。

SDP 只负责描述“有哪些服务以及怎样连接”，业务数据由对应 Profile 传输。例如，SPP 设备的 SDP 记录会提供 RFCOMM 通道号，A2DP 设备的记录会描述 Audio Source 或 Audio Sink 能力。

## 6. 配对、认证与加密

经典蓝牙的安全过程会根据双方能力和 Profile 要求执行。常见步骤如下：

1. 双方通过 Link Manager 交换安全能力。
2. 双方生成或读取 Link Key。
3. 需要加密时，Controller 使用 Link Key 建立加密链路。
4. Host 保存配对材料，使下一次连接可以直接认证。

Bluetooth 2.1 引入 **SSP（Secure Simple Pairing）**，常见关联方式包括 Just Works、Numeric Comparison、Passkey Entry 和 Out of Band。旧设备可能使用固定 PIN 或可变 PIN。应用应根据设备显示能力选择关联方式，并在用户确认事件到达后继续配对流程。

安全配置需要区分三个状态：

| 状态      | 含义                   |
| ------- | -------------------- |
| 已发现     | 设备可以被 Inquiry 找到     |
| 已连接     | ACL 链路已经建立           |
| 已配对或已加密 | 双方已经完成认证，链路具有对应的安全保护 |

已连接的设备不一定已经配对，已配对的设备也可能因为服务或权限检查失败而无法使用目标 Profile。

## 7. ACL、SCO 与 eSCO 数据通道

### 7.1 ACL

**ACL（Asynchronous Connection-Less）** 用于异步数据，承载 L2CAP、SDP、RFCOMM、A2DP 控制信令、HID 和 PAN 等内容。ACL 数据允许重传，适合文件、串口和控制消息。

### 7.2 SCO 与 eSCO

**SCO（Synchronous Connection-Oriented）** 和 **eSCO（Extended SCO）** 用于有明确时间要求的语音数据。它们占用预留时隙，常见于 HFP 或 HSP 的通话音频。

| 通道   | 典型用途                | 传输特点             |
| ---- | ------------------- | ---------------- |
| ACL  | SPP、A2DP 控制、HID、PAN | 异步、可重传、适合一般数据    |
| SCO  | 早期语音链路              | 固定时序，适合持续语音      |
| eSCO | HFP 语音链路            | 增加包类型和重传能力，参数更灵活 |

A2DP 的媒体数据通过 ACL 传输，HFP 的通话语音通常通过 SCO 或 eSCO 传输。两者都属于蓝牙音频，传输通道和 Profile 设计不同。

## 8. L2CAP、PSM 与 RFCOMM

### 8.1 L2CAP

L2CAP 为上层提供逻辑信道。每条信道使用 CID 标识连接端点，固定服务通常使用已分配的 PSM，自定义服务可以通过动态 PSM 建立信道。

L2CAP 负责以下工作：

- 将多个上层协议复用到同一条 ACL 链路。
- 将较大的上层数据分段为 Controller 可以发送的包。
- 在接收端把分段重新组成上层数据单元。
- 根据模式提供流量控制、重传或增强可靠性。

应用层需要自行定义消息边界。例如一次 send 可能对应多次接收，也可能多条消息合并到一次接收中。串口协议通常使用长度字段、固定帧长度或结束标志完成分帧。

### 8.2 RFCOMM

**RFCOMM** 在 L2CAP 上模拟串口通信。SPP 设备通常通过 RFCOMM 提供串口服务，主机侧可以看到一个虚拟 COM 端口。RFCOMM 的“串口”只描述上层数据接口，底层仍然是 ACL、L2CAP 和跳频链路。

SPP 连接过程可以写成：

~~~text
Inquiry / Page
    └── ACL 连接
        └── SDP 查询 Serial Port Service
            └── 获得 RFCOMM Channel
                └── 建立 RFCOMM DLCI
                    └── 打开串口数据通道
~~~

## 9. 常见 Profile

| Profile | 用途           | 主要数据路径                                |
| ------- | ------------ | ------------------------------------- |
| A2DP    | 单向高质量音乐播放    | ACL + L2CAP，媒体通常使用 RTP 封装             |
| AVRCP   | 音乐播放控制       | ACL + L2CAP，控制播放、暂停、切歌                |
| HFP     | 手机免提和通话      | RFCOMM 控制信令 + SCO/eSCO 语音             |
| HSP     | 耳机和耳机网关的基本语音 | RFCOMM 控制信令 + SCO 语音                  |
| SPP     | 串口线缆替代       | RFCOMM + L2CAP                        |
| HID     | 键盘、鼠标和手柄     | HID Control / Interrupt L2CAP Channel |
| PAN     | 个人区域网络       | BNEP + L2CAP                          |

### 9.1 A2DP 的 Source 与 Sink

- **A2DP Source** 产生音频，例如手机或电脑。
- **A2DP Sink** 接收音频并播放，例如蓝牙耳机或音箱。
- A2DP 的媒体发送和接收属于 ACL 数据路径，音频数据经过 Profile 选择的 Codec 编码。
- AVRCP 可以与 A2DP 同时使用，用于播放控制和媒体信息查询。

### 9.2 HFP 的 Audio Gateway 与 Hands-Free

- **Audio Gateway（AG）** 通常是手机，管理蜂窝通话或语音服务。
- **Hands-Free（HF）** 通常是车载设备或耳机，提供麦克风、扬声器和通话按键。
- RFCOMM 通道承载 AT 命令和状态，SCO/eSCO 承载语音采样。

## 10. ESP-IDF 经典蓝牙开发

### 10.1 支持范围

原始 ESP32 芯片支持 Bluetooth Classic 与 BLE 双模。ESP32-S3、ESP32-C3、ESP32-C6 和 ESP32-H2 主要支持 BLE，不能通过 NimBLE 或 Bluedroid 建立 BR/EDR 链路。使用其他型号时，需要查看对应芯片的 Bluetooth 功能表和当前 ESP-IDF 版本的组件说明。

ESP-IDF 中，经典蓝牙 Host 常用 Bluedroid。常见入口包括：

| 功能             | 典型 API 组                                            |
| -------------- | --------------------------------------------------- |
| Controller     | esp_bt_controller_init()、esp_bt_controller_enable() |
| Bluedroid Host | esp_bluedroid_init()、esp_bluedroid_enable()         |
| GAP            | esp_bt_gap_*()                                      |
| SPP            | esp_spp_*()                                         |
| A2DP           | esp_a2d_*()、esp_a2d_sink_*()                        |
| HFP            | esp_hf_client_*()、esp_hf_ag_*()                     |

### 10.2 初始化顺序

下面的顺序适合仅启用经典蓝牙的应用。具体 Profile 的回调注册和初始化函数，需要按照当前 ESP-IDF 示例补全。

~~~c
nvs_flash_init();

esp_bt_controller_config_t bt_cfg = BT_CONTROLLER_INIT_CONFIG_DEFAULT();
esp_bt_controller_init(&bt_cfg);
esp_bt_controller_enable(ESP_BT_MODE_CLASSIC_BT);

esp_bluedroid_init();
esp_bluedroid_enable();

esp_bt_gap_register_callback(gap_callback);
esp_spp_register_callback(spp_callback);
esp_spp_init(ESP_SPP_MODE_CB);
~~~

如果应用需要同时运行 Classic 与 BLE，可以使用 ESP_BT_MODE_BTDM，并根据内存情况启用对应 Controller 功能。仅使用 Classic 时，可以在 `esp_bt_controller_init()` 之前调用 `esp_bt_controller_mem_release(ESP_BT_MODE_BLE)` 释放 BLE Controller 专用内存。执行后无法再初始化 BLE Controller。

### 10.3 SPP Server 的典型流程

~~~text
初始化 NVS
    └── 初始化并启用 Bluetooth Controller
        └── 初始化并启用 Bluedroid
            ├── 注册 GAP 回调
            ├── 注册 SPP 回调
            ├── 设置设备名称和可发现状态
            ├── 启动 SPP
            └── 创建 SPP Service
                    └── 处理 OPEN / DATA_IND_EVT / CLOSE 事件
~~~

SPP 服务启动后，手机或电脑通过 Inquiry 找到设备，再通过 SDP 取得 RFCOMM 服务信息。连接建立事件到达后，应用保存 handle，收到数据事件时根据长度读取 data，发送数据时检查 API 返回值和发送完成事件。

### 10.4 事件处理原则

- GAP 回调处理 Inquiry、Page、配对、认证、加密和远端名称事件。
- Profile 回调处理服务启动、连接、断开、数据接收和发送完成事件。
- 回调中只执行必要的状态更新和数据转移，耗时任务交给独立任务。
- 每个 handle 都要和连接状态绑定；收到 CLOSE 或断链事件后清理对应状态。
- 发送数据前检查链路状态、数据长度和 Controller 缓冲资源。

## 11. 经典蓝牙与 BLE 的选择

| 需求 | 更适合的通信方式 | 原因 |
|---|---|---|
| 蓝牙耳机音乐播放 | Classic A2DP | 现有音频设备广泛支持 A2DP |
| 电话免提和通话 | Classic HFP | 语音控制信令和 SCO/eSCO 已定义 |
| 电脑虚拟串口 | Classic SPP | 主机系统有成熟的 RFCOMM 支持 |
| 电池供电传感器 | BLE GATT | 广播和连接参数适合低功耗运行 |
| 键盘、鼠标、手柄 | HID 或 BLE HID | 取决于主机兼容性和功耗要求 |
| 自定义短消息 | BLE GATT 或 Classic RFCOMM | 根据芯片支持、主机端 API 和功耗选择 |

需要连接普通蓝牙耳机、车载系统或传统串口模块时，先确认对端支持的 Profile。对端只支持 A2DP、HFP 或 SPP 时，BLE GATT 服务无法替代对应的 Classic Profile。

## 12. 调试清单

1. 确认芯片具备 BR/EDR Controller，确认当前 ESP-IDF 组件启用了 Classic 功能。
2. 确认 Controller 模式、Host 模式和内存配置与应用需求一致。
3. 确认设备已经开启 Inquiry Scan、Page Scan 和目标 Profile 的服务。
4. 先观察 GAP 事件，再观察 SDP 结果，最后判断 Profile 是否建立。
5. 配对失败时检查 SSP 关联方式、PIN、用户确认事件和已保存的 Link Key。
6. SPP 数据异常时检查 RFCOMM Channel、连接 handle、数据分帧和长度字段。
7. A2DP 无声音时分别检查 A2DP 状态、Codec、音频回调、I2S 输出和音频时钟。
8. HFP 通话异常时分别检查 RFCOMM 控制信令与 SCO/eSCO 音频链路。
9. 记录 HCI、GAP、SDP 和 Profile 事件的时间顺序，避免把“设备可发现”“ACL 已连接”和“业务可用”混为一谈。
