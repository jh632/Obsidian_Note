# 嵌入式八股文

## 1 MCU 上电后 main 函数之前发生了什么？

```
上电复位
↓
从复位向量取启动地址
↓
执行启动文件 startup
↓
初始化栈指针
↓
拷贝 .data 段到 RAM
↓
清零 .bss 段
↓
SystemInit，配置时钟
↓
调用 main
```

| 段         | 含义                             |
| ---------- | ------------------------------ |
| `.text`    | 代码段，通常在 Flash              |
| `.rodata`  | 只读常量                        |
| `.data`    | 已初始化全局/静态变量，运行在 RAM，初值在 Flash |
| `.bss`     | 未初始化全局/静态变量，启动时清零    |
| heap       | 动态分配区                      |
| stack      | 函数调用栈                      |

## 3 Flash 操作

### 3.1 内部 Flash

MCU 内部 Flash 通常存放：

- 程序代码
- 常量
- 默认参数
- 少量配置
- Bootloader
- App 固件

程序里的：

```c
const char name[] = "device";
```

通常在 Flash 的 `.rodata` 段。代码本身在 `.text` 段。

### 3.2 外部 Flash

外部 Flash 常见接口：

- SPI Flash
- QSPI Flash
- OSPI Flash
- Parallel NOR Flash
- NAND Flash

常用于：

- 大容量固件
- OTA 分区
- 文件系统
- 字库
- 图片资源
- 日志

ESP32 的程序通常就在外部 SPI Flash 里。

### 3.3 Flash 规则

Flash 擦除后通常是 `0xFF`。

写入只能 `1 → 0`，不能直接 `0 → 1`。

所以要从 `0` 变回 `1`，**必须擦除**。

## 5 FreeRTOS 临界区如何实现

FreeRTOS 提供了两组宏来进入/退出临界区：

| 适用范围   | 进入临界区                          | 退出临界区                            | 原理                                                     |
| ---------- | ----------------------------------- | ------------------------------------- | -------------------------------------------------------- |
| **任务级** | `taskENTER_CRITICAL()`             | `taskEXIT_CRITICAL()`                | 通过 `ulPortSetInterruptMask()` 关中断，并维护嵌套计数（可嵌套调用） |
| **中断级** | `taskENTER_CRITICAL_FROM_ISR()`    | `taskEXIT_CRITICAL_FROM_ISR( x )`   | 只关闭优先级较低的或全部可配置的中断（具体由移植层决定）          |

**核心特点**：

- 基于**关中断**实现，进入临界区后不会被其他任务或中断打断（除非是最高优先级、不可屏蔽的中断）。
- 执行速度快，适合保护**极短的、不能有任何上下文切换**的操作，例如修改全局变量、链表节点操作。
- **不能**睡眠、阻塞或等待任何事件（因为关中断后无法响应系统 tick，调度器也会被冻结）。

**实现细节**：

```c
step1:
portDISABLE_INTERRUPTS()
// 关中断等价 __set_BASEPRI(configMAX_SYSCALL_INTERRUPT_PRIORITY);
// 例如设置 BASEPRI 寄存器为 0x50
// 优先级 >= 0x50 的中断被屏蔽
// 优先级 < 0x50 的高优先级中断继续运行

step2:
uxCriticalNesting++;
// 增加嵌套计数，关中断允许嵌套
// 只有 uxCriticalNesting == 0 才会重启中断

step3:
if( uxCriticalNesting == 1 )
{
    configASSERT(
        ( portNVIC_INT_CTRL_REG & portVECTACTIVE_MASK ) == 0
        // 判断当前是否运行在中断
    );
}
```

## 6 FreeRTOS 中的互斥锁和信号量

### 6.1 本质区别

**信号量（Semaphore）** — 同步工具，用于通知某个事件发生了。

**互斥锁（Mutex）** — 资源保护工具，用于保证同一时间只有一个任务访问共享资源。

### 6.2 拥有者（Owner）概念

**Semaphore** — 没有拥有者，可以在不同任务 take 和 give。

**Mutex** — `xSemaphoreTake(mutex)` 会把当前任务注册为拥有者，`xSemaphoreGive(mutex)` 只有拥有者才能释放。

### 6.3 优先级继承（Priority Inheritance）

**优先级反转问题：**

如果有高优先级任务 H、中优先级任务 M、低优先级任务 L：

1. **时刻 1**：L 获得 Mutex — `xSemaphoreTake(mutex);`
2. **时刻 2**：H 想获取 Mutex — `xSemaphoreTake(mutex);` 发现被占用，H 阻塞。
3. **时刻 3**：M 开始运行 — 由于 H 被阻塞，L 优先级低，结果 M 一直运行，L 得不到 CPU。

结果：H 等 L 释放锁，L 等 CPU，CPU 被 M 占着，形成**优先级反转（Priority Inversion）**。

**Mutex 解决方案：优先级继承（Priority Inheritance）**

当 L 持有 H 等待的 mutex，L 任务的优先级会临时提升到 H 的优先级，从而让 L 尽快运行释放锁。

## 7 Task Notify 为什么轻量化

> Task Notify 轻量，是因为它直接使用任务 TCB 里的成员变量实现通知，不需要额外创建内核对象。

| 机制           | 是否需要额外对象 | 底层             |
| -------------- | ---------------- | ---------------- |
| Semaphore      | 需要             | Queue 对象       |
| Mutex          | 需要             | Queue 对象       |
| EventGroup     | 需要             | EventGroup 对象  |
| **Task Notify** | **不需要**      | **TCB 成员变量** |

例如：

```
TaskA
 └─ TCB
     ├─ priority
     ├─ stack
     ├─ notify_value
     └─ notify_state
```

通知时：

```c
vTaskNotifyGive(TaskA);
```

本质就是：

```c
TaskA->notify_value++;
TaskA->notify_state = notified;
```

然后唤醒任务。

而 Semaphore 需要经过：Semaphore 对象 → Queue 控制块 → 等待链表 → 资源管理 → 唤醒任务，中间多了一层内核对象。

所以 Task Notify 具有：

- 更少 RAM 占用（通常不需要额外内存）
- 更少 CPU 开销
- 更快的 ISR → Task 通知路径

在 FreeRTOS 官方文档中，Task Notification 被称为：

> **A lightweight and fast direct-to-task communication mechanism**（轻量且快速的直接任务通信机制）。

## 9 结构体成员的内存布局

结构体的内存布局由编译器的**对齐规则**决定，成员按**声明顺序**依次排列，但编译器会在成员之间和结构体末尾插入**填充字节（padding）**以符合对齐要求。

```c
struct example {
    char   a;   // 1 byte, offset 0
                // 3 bytes padding
    int    b;   // 4 bytes, offset 4
    short  c;   // 2 bytes, offset 8
                // 2 bytes padding (尾部填充)
};  // 总大小 12 bytes
```

**布局规则：**

1. 每个成员的起始偏移必须是其自身对齐值（通常是 `sizeof`）的整数倍。
2. 结构体的总大小必须是最大成员对齐值的整数倍（尾部填充）。
3. 成员按声明顺序排列，编译器不会重排。

> 成员顺序影响结构体大小，把大成员放在前面、小成员放在一起可以减少 padding，节省空间。

## 10 为什么会有对齐的要求？如果不对齐会发生什么问题？

### 10.1 为什么需要对齐

**硬件层面的原因**：CPU 访问内存时不是逐字节访问的，而是按字（word）读取。

| CPU 位宽 | 总线宽度 | 一次读取 |
| -------- | -------- | -------- |
| 32 位    | 32 位    | 4 字节   |
| 64 位    | 64 位    | 8 字节   |

- 如果 int 存放在 **4 字节对齐**的地址，CPU 只需要**一次**内存访问。
- 如果 int 存放在**未对齐**的地址，CPU 可能需要**两次**内存访问并做拼接。

### 10.2 不对齐会发生的问题

1. **性能下降**：未对齐访问需要两次读取+拼接，性能损失可达 2~3 倍甚至更多。
2. **硬件异常**：ARM Cortex-M（默认配置下）、MIPS、早期 RISC 架构会触发 **HardFault** 或 **Alignment Fault**。
3. **原子操作失败**：C11 原子操作要求地址自然对齐，未对齐会导致原子性无法保证。
4. **DMA 传输错误**：DMA 控制器通常要求缓冲区地址对齐到一定边界。

> x86 能容忍未对齐访问（只是慢），但 ARM Cortex-M 默认设置下会直接触发 HardFault。

## 11 不同的对齐方式，整个结构体的大小会变吗？

**会变。** 对齐方式直接影响 padding 的数量和位置。

| 对齐方式                              | 效果              | 大小变化       |
| --------------------------------- | --------------- | ---------- |
| **自然对齐（默认）**                      | 每个成员按自身大小对齐     | 参考大小       |
| **`#pragma pack(1)`**             | 强制 1 字节对齐，消除填充  | 最小         |
| **`__attribute__((packed))`**     | 同上，GCC/ARMCC 可用 | 最小         |
| **`__attribute__((aligned(n)))`** | 增大结构体整体对齐值      | 变大（尾部填充增多） |
|                                   |                 |            |

**示例对比：**

```c
struct S_normal {
    char c;  // offset 0
             // 3 bytes padding
    int  i;  // offset 4
    short s; // offset 8
             // 2 bytes padding (tail)
};  // 12 bytes

struct __attribute__((packed)) S_packed {
    char c;  // offset 0
    int  i;  // offset 1
    short s; // offset 5
};  // 7 bytes（无任何填充）
```

**结论：对齐方式改变 → padding 改变 → 结构体大小改变。**

## 12 结构体对齐填充的碎片是谁填充进去的？

**是编译器填充的。** 具体来说是编译器在生成结构体内存布局时自动插入的。

| 角色             | 职责                                                         |
| ---------------- | ------------------------------------------------------------ |
| **C 语言标准**   | 规定成员按声明顺序排列，允许编译器在成员之间和末尾添加填充   |
| **编译器后端**   | 根据目标架构的 ABI、对齐规则、`#pragma pack` 等指令决定 padding 的大小和位置 |
| **程序员**       | 无法在代码层面直接控制填充字节（它们是隐式的）               |

### 填充字节的值是什么

编译器**不会主动初始化 padding 字节**，它们的内容是内存中已有的随机值：

```c
struct S s;
// padding 字节的值 = 栈/堆上的遗留数据，未定义
```

```c
// 错误做法：用 memcmp 比较结构体
memcmp(&s, &s2, sizeof(s));  // 结果不可靠，padding 字节不同

// 正确做法：先 memset 清零
memset(&s, 0, sizeof(s));
```

## 13 填充是在编译的还是运行的哪个阶段做的？

### 编译阶段（编译期的布局阶段）

| 阶段         | 行为                                                         |
| ------------ | ------------------------------------------------------------ |
| **编译期**   | 解析 struct 定义 → 计算成员偏移 → 插入 padding → 确定总大小 → 生成调试元数据 |
| **汇编/链接期** | 布局已固定，成员访问使用编译时计算好的偏移量               |
| **运行期**   | 只按编译期确定的布局分配内存，不做任何动态填充               |

### 验证方法

```c
struct S { char c; int i; };
// 编译时：c 在 offset 0，padding 占 offset 1-3，i 在 offset 4
// sizeof(struct S) = 8 在编译期已知

struct S s;        // 运行时只分配 sizeof(S) 字节
malloc(sizeof(S)); // 同上，堆分配
```

### 例外

- **灵活数组成员（Flexible Array Member）**：C99 允许结构体最后一个成员是 `arr[]`，其大小在运行时决定。
- 但结构体本身的对齐布局（所有 padding 的位置）仍然是**编译时决定**的。

> **总结：** 所有 padding 的决策和布局在**编译期**完成，运行期不做任何对齐填充操作。

## 14 FreeRTOS的任务切换是如何实现的

### **核心触发源**
FreeRTOS 主要通过以下两种方式触发任务切换，两者的最终目的都是**将 PendSV 中断寄存器悬起（手动置 1）**
- **主动触发（系统调用）**：任务因等待资源阻塞（如 `vTaskDelay()`、信号量）或主动让出 CPU（调用 `taskYIELD()`）。
- **被动触发（时间片轮转）**：由 `SysTick` 滴答定时器中断触发。当时间片耗尽或有更高优先级任务就绪时，在 SysTick 中断中悬起 PendSV

### pendsv中断和核心步骤

```
当前任务运行 ──> 触发 PendSV ──> [1. 硬件自动压栈] ──> [2. 软件手动压栈] ──> [3. 切换 TCB 指针] ──> [4. 软件手动出栈] ──> [5. 硬件自动出栈] ──> 新任务运行
```

1. 保存当前任务上下文（压栈）

- **硬件自动压栈**：进入 PendSV 中断时，Cortex-M 硬件会自动将当前任务的 `xPSR`, `PC`, `LR`, `R12`, `R3-R0` 寄存器压入该任务的栈（PSP）中。
- **软件手动压栈**：在汇编代码中，通过指令（如 `STMDB`）将剩余的 `R11-R4` 寄存器手动压入该任务的栈中。
- **更新栈顶**：将当前任务最新的栈指针（SP）保存到该任务的任务控制块 `pxCurrentTCB->pxTopOfStack` 中。
2. 选择最高优先级的就绪任务

- 汇编代码调用 C 语言函数 `vTaskSwitchContext()`。
- 调度器根据优先级列表，通过查表算法（硬件支持 `CLZ` 算力前导零指令，实现 O(1) 复杂度），寻找当前处于就绪态的最高优先级任务。
- 将全局指针 `pxCurrentTCB` 指向这个新任务。 
1. 恢复新任务上下文（出栈）

- **读取新栈顶**：从新任务的 `pxCurrentTCB->pxTopOfStack` 中取出其栈指针（SP）。
- **软件手动出栈**：使用汇编指令（如 `LDMIA`）将新任务栈中的 `R11-R4` 寄存器值弹射恢复到 CPU 寄存器中。
- **退出中断与硬件自动出栈**：执行中断返回指令（修改 `EXC_RETURN` 启用进程栈指针 PSP）。退出中断时，硬件自动将新任务栈中的 `R0-R3`, `R12`, `LR`, `PC`, `xPSR` 弹出到 CPU 寄存器，CPU 随之跳转到新任务上次被暂停的代码位置继续执行
### 为什么选择pendsv中断

为了防止中断嵌套错乱。PendSV 的优先级被配置为**最低**。当 SysTick 或其他外设中断触发任务切换时，它不会立即执行，而是等待所有高优先级的中断服务程序（ISR）全部执行完毕，才安全地切换上下文，避免了中断被延迟或触发 UsageFault。
