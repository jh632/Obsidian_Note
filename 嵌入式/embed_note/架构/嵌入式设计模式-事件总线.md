# 事件总线（Event Bus）/ 发布订阅

> 参考实现：Zephyr zbus（官方消息总线子系统，2022.12 / Zephyr 3.3 引入，作者 Rodrigo Peixoto）

## 1. 一句话

> **模块之间不直接互相调用，而是通过一个统一的"事件通道"发布和接收消息。发布者不需要知道订阅者是谁。**

事件总线适合解决这种问题：多个模块互相依赖、状态变化要通知多方（UI 要弹窗、日志要记录、另一个模块要停止工作）。

```
              ┌─────────────┐
WebSocket ───►│             │
USB ─────────►│  Event Bus  │
Power ───────►│             │
Collection ──►│             │
              └──────┬──────┘
                     │
           ┌─────────┼─────────┐
           ▼         ▼         ▼
         System     OTA       UI
```

## 2. 它是观察者模式的升级

[[嵌入式设计模式-观察者]]解决的是"Subject 通知多个 Observer"；事件总线把两者都解耦了：

| | 观察者模式 | 事件总线 |
| --- | --- | --- |
| 主题（Subject） | 持有观察者列表，自己发通知 | 发布者只管 publish，不知道谁在听 |
| 观察者 | 注册到具体 Subject | 订阅事件，不知道谁发的 |
| 通信对象 | 1 个 Subject → N 个 Observer | N 个发布者 → N 个订阅者（多对多） |
| 通道 | 无，直接回调 | 有，事件/通道是显式的中间层 |

事件总线 ≈ 观察者模式去掉"双方认识"这一步：**发布者不知道订阅者，订阅者不知道发布者。**

## 3. 核心概念

### 3.1 Event / Command / State 要区分（最重要的设计决策）

| 概念 | 语义 | 命名 | 例子 |
| --- | --- | --- | --- |
| **Event** | 已经发生了什么（事实） | `EVENT_xxx` | `EVENT_LOW_BATTERY`, `EVENT_OTA_FAILED` |
| **Command** | 要求某个模块做什么（请求） | `CMD_xxx` | `CMD_START_OTA`, `CMD_SHUTDOWN` |
| **State** | 当前状态（状态机） | `SYSTEM_xxx` | `SYSTEM_IDLE`, `SYSTEM_SAMPLING` |

典型链路：外部输入 → Event → 策略仲裁（允许/拒绝）→ Command → 模块执行 → 新 Event → UI。

**Event 与 Command 混在一起是最常见的错误**：`EVENT_START_OTA` 这种命名既是"请求执行"又是"已发生"，语义会糊掉。

### 3.2 事件总线 vs 消息队列（不是一回事）

| | FreeRTOS Queue / k_msgq | Event Bus |
| --- | --- | --- |
| 主要用途 | 消息传输（数据搬运） | 事件通知 |
| 通信关系 | 通常点对点 | 通常一对多广播 |
| 发布者是否知道消费者 | 通常知道 | 不需要 |
| 解耦程度 | 一般 | 很强 |
| 是否适合携带数据 | 很适合 | 可以，但通知为主 |
| 适合状态变化通知 | 一般 | 非常适合 |

传感器数据流（ISR → 处理任务）用队列；模块间"发生了什么事"用事件总线。两者共存，不是替代关系。

## 4. Zephyr zbus 设计

### 4.1 设计原则

1. **编译期静态定义**：通道（channel）、观察者（observer）、订阅关系全部由宏 + 链接器 iterable section 静态布局，零动态分配、确定性好——适合 MCU
2. **发布者不知道订阅者**：publish 只写消息 + 通知，不关心谁处理
3. **VDED（虚拟分布式事件分发器）**：分发逻辑在**发布者上下文**执行（线程或 ISR）
4. **同步与异步两种观察者**：listener 同步回调；subscriber 异步排队
5. **优先级提升（HLP）**：可选开关，发布者临时提升到最高观察者优先级，防止优先级反转

### 4.2 三种观察者类型（重点）

| 类型 | 宏 | 通知方式 | 何时用 |
| --- | --- | --- | --- |
| **Listener**（同步） | `ZBUS_LISTENER_DEFINE(name, cb)` | 发布者上下文直接调用回调，通道加锁期间执行 | 快速、不阻塞的处理（更新状态、标志） |
| **Subscriber**（异步） | `ZBUS_SUBSCRIBER_DEFINE(name, queue_size)` | 往订阅者的 k_msgq 塞一个 **channel 指针**；订阅者拿到指针后自己 `zbus_chan_read()` 拷贝 | 慢处理、任务阻塞等待；**无投递保证**（快速连续发布可能被覆盖） |
| **Message Subscriber**（异步+可靠） | `ZBUS_MSG_SUBSCRIBER_DEFINE(name)` | 往订阅者的 k_fifo 塞一个 **完整消息拷贝**（net_buf） | 每条消息都不能丢的慢消费者 |

### 4.3 代码示例（官方 API）

```c
/* 1. 定义消息类型 */
struct acc_msg {
    float x, y, z;
};

/* 2. 定义通道（静态，链接期布局）：
 *    参数 = 名字, 消息类型, 校验函数(可空), user_data, 观察者列表, 消息初始值
 *    观察者列表顺序 = 通知优先级，第一个最高 */
ZBUS_CHAN_DEFINE(acc_chan, struct acc_msg, NULL, NULL,
                 ZBUS_OBSERVERS(acc_listener, acc_sub),
                 ZBUS_MSG_INIT(.x = 0, .y = 0, .z = 0));

/* 3a. Listener：同步回调（发布者上下文执行，保持短小） */
void acc_listener_cb(const struct zbus_channel *chan)
{
    /* 回调内直接只读访问，无需加锁 */
    const struct acc_msg *m = zbus_chan_const_msg(chan);
    update_screen(m);
}
ZBUS_LISTENER_DEFINE(acc_listener, acc_listener_cb);

/* 3b. Subscriber：异步，自己起任务读 */
ZBUS_SUBSCRIBER_DEFINE(acc_sub, 4);   /* 队列能存 4 个 channel 指针 */
void acc_sub_task(void *arg)
{
    while (1) {
        const struct zbus_channel *chan;
        if (zbus_sub_wait(&acc_sub, &chan, K_FOREVER) != 0)
            continue;
        struct acc_msg m;
        if (zbus_chan_read(chan, &m, K_MSEC(500)) == 0)
            process(&m);
    }
}

/* 4. 发布（任意模块，任意线程/ISR；ISR 中 timeout 必须 K_NO_WAIT） */
struct acc_msg m = { .x = 1.0, .y = 2.0, .z = 9.8 };
zbus_chan_pub(&acc_chan, &m, K_MSEC(100));
```

跨文件使用：`ZBUS_CHAN_DECLARE(acc_chan);` / `ZBUS_OBS_DECLARE(acc_sub);` 声明 extern。

其他常用 API：

```c
zbus_chan_notify(&acc_chan, K_NO_WAIT);          /* 只通知不写消息 */
zbus_chan_claim(&acc_chan, K_MSEC(100));         /* 独占通道原地改 */
memcpy(zbus_chan_msg(&acc_chan), &m, sizeof(m));
zbus_chan_finish(&acc_chan);                     /* 释放，之后 notify */
zbus_sub_wait_msg(&msg_sub, &chan, &msg, K_FOREVER); /* msg subscriber 直接收拷贝 */
zbus_obs_set_enable(&acc_listener, false);       /* 运行时开关订阅 */
```

### 4.4 实现剖析（zbus.c 关键流程）

**数据结构：**

```c
struct zbus_channel {           /* 通道（静态只读部分） */
    const char *name;
    void       *message;        /* 指向静态分配的共享消息内存 */
    size_t      message_size;
    void       *user_data;
    bool (*validator)(const void *msg, size_t msg_size);  /* 发布前校验，失败拒绝 */
    struct zbus_channel_data *data;
};

struct zbus_channel_data {      /* 通道可变部分 */
    int16_t observers_start_idx;   /* 观察者在全局数组中的区间 [start, end) */
    int16_t observers_end_idx;
    struct k_sem sem;              /* 访问控制信号量（读写/发布互斥） */
};

struct zbus_observer {          /* 观察者 = listener 或 subscriber */
    enum zbus_observer_type type;  /* LISTENER / SUBSCRIBER / MSG_SUBSCRIBER / ASYNC_LISTENER */
    struct zbus_observer_data *data;  /* 含 enabled 开关 */
    union {
        struct k_msgq *queue;       /* subscriber：通知队列（存 channel 指针） */
        void (*callback)(const struct zbus_channel *chan);  /* listener */
        struct k_fifo *message_fifo;  /* msg subscriber：完整消息 */
    };
};

struct zbus_channel_observation { /* 通道→观察者 的静态关联（链接期生成） */
    const struct zbus_channel *chan;
    const struct zbus_observer *obs;
};
```

**静态布局：iterable section（最妙的设计）**

`ZBUS_CHAN_DEFINE` / `ZBUS_LISTENER_DEFINE` 展开后，把 channel、observer、observation 都放进链接器收集的 section（`STRUCT_SECTION_ITERABLE`）。启动时 `_zbus_init()`（SYS_INIT）遍历所有 observation，给每个 channel 算出 `observers_start_idx / observers_end_idx` 连续区间。

这样发布时**不需要遍历链表**，只用一个连续区间循环，零分配、O(观察者数) 且可预测——这是它比"运行时注册数组"更适合 MCU 的原因。

**发布流程（zbus_chan_pub）：**

```text
zbus_chan_pub(chan, msg, timeout)
  │ 1. validator(msg) 校验 → 非法拒绝 (-ENOMSG)
  │ 2. chan_lock(): k_sem_take（可选：优先级提升防反转）
  │ 3. memcpy 消息 → chan->message（共享内存，后续 reader 读到同一份）
  │ 4. _zbus_vded_exec(): 遍历 observers [start, end)
  │      ├─ LISTENER        → 直接调回调（同步，通道仍加锁！）
  │      ├─ SUBSCRIBER      → k_msgq_put(&chan)（只通知指针，异步）
  │      ├─ MSG_SUBSCRIBER  → net_buf 克隆完整消息 → k_fifo_put（异步+可靠）
  │      └─ ASYNC_LISTENER  → 拷贝消息 + k_work_submit（工作队列延迟执行）
  │ 5. chan_unlock(): k_sem_give（恢复优先级）
```

要点：
- **同步 listener 在发布者上下文执行且通道加锁**——回调里绝不能阻塞、不能发布同一通道（死锁），必须短小
- 普通 subscriber 拿到的是 channel 指针，读时要自己 `zbus_chan_read`（内部再对信号量加锁拷贝）——所以**无投递保证**：连续两次 publish，慢的订阅者可能读到第二次的数据
- ISR 中 publish 必须是 `K_NO_WAIT`（有断言强制）
- 消息可靠性排序：listener / msg subscriber（可靠）> subscriber（会被覆盖）

## 5. 在 FreeRTOS / 裸机上的最小实现思路

zbus 依赖 Zephyr 内核（信号量、消息队列、链接器 section）。移植到 FreeRTOS 的等价做法：

```c
/* 最小实现：静态数组版 listener（同步分发，线程安全靠互斥锁） */

typedef enum {
    EVENT_POWER_LOW,
    EVENT_POWER_CRITICAL,
    EVENT_COLLECTION_STARTED,
    EVENT_COLLECTION_FAILED,
    EVENT_OTA_STARTED,
    EVENT_OTA_FINISHED,
    EVENT_OTA_FAILED,
    EVENT_OTA_REQUEST,      /* 需要区分 Event/Command 时拆成 CMD_ 前缀 */
    EVENT_COUNT,
} event_id_t;

typedef void (*event_handler_t)(event_id_t id, const void *data, void *ctx);

typedef struct {
    event_handler_t handler;
    void           *ctx;
    bool            enabled;
} event_subscription_t;

#define MAX_SUBS_PER_EVENT 4

static event_subscription_t s_subs[EVENT_COUNT][MAX_SUBS_PER_EVENT];
static SemaphoreHandle_t s_lock;   /* 保护订阅表（发布时短临界区） */

void event_subscribe(event_id_t id, event_handler_t h, void *ctx);
void event_publish(event_id_t id, const void *data);

void event_publish(event_id_t id, const void *data)
{
    /* 快照订阅表到局部数组（拷贝 4 个指针），释放锁后再回调，
       避免回调里 subscribe/unsubscribe 造成悬垂 */
    event_subscription_t local[MAX_SUBS_PER_EVENT];
    xSemaphoreTake(s_lock, portMAX_DELAY);
    memcpy(local, s_subs[id], sizeof(local));
    xSemaphoreGive(s_lock);

    for (int i = 0; i < MAX_SUBS_PER_EVENT; i++) {
        if (local[i].handler && local[i].enabled)
            local[i].handler(id, data, local[i].ctx);
    }
}
```

需要异步订阅者时，扩展方向：每个订阅者带一个 FreeRTOS 队列，publish 时 `xQueueSendFromISR` / `xQueueSend` 塞事件副本，订阅者任务阻塞在 `xQueueReceive`——对应 zbus 的 subscriber / msg subscriber 两种模式。

## 6. 使用注意（不是银弹）

1. **调用关系变隐式**：`event_publish(EVENT_LOW_BATTERY)` 不知道谁会响应。补救：
   - 事件/命令定义统一放在一个 `app_event.h`
   - 订阅关系集中登记（类似 zbus 用静态宏集中声明），可审查
   - 命名严格 `EVENT_xxx` / `CMD_xxx`
2. **内部调用不绕总线**：`ota_download()` 是模块内部动作，别发事件。总线只表达"发生了其他模块可能关心的事"
3. **同步回调要短**：listener 在发布者上下文执行，阻塞会卡住发布者（zbus 还加着锁）
4. **防"万能垃圾桶"**：模块别偷偷订阅大量事件，否则 Event Bus 退化成全局变量
