# 嵌入式函数设计原则

> 来源：[写了这么多年嵌入式C，你真的会设计函数吗？](https://mp.weixin.qq.com/s/kT9aArkGL9NFQ-OvoyCgcQ) — 一枚嵌入式码农

## 1. 一句话

> 入参显式、返回值明确、单一职责、控制长度——好函数的标准在嵌入式环境下还有栈安全和可重入的额外约束。

## 2. 入参设计

### 2.1 显式依赖优于隐式依赖

❌ 通过全局变量偷偷传入信息：

```c
// 调用者看不出函数依赖什么数据
void Protocol_Parse(void);
```

✅ 显式声明所需信息：

```c
void Protocol_Parse(const uint8_t *data, size_t len);
```

### 2.2 入参个数控制

| 参数个数 | 评价 |
|---------|------|
| ≤ 3 | ✅ 最佳 |
| 4–5 | ⚠️ 可接受 |
| > 5 | ❌ 考虑用结构体打包 |

超过 3 个参数时，用结构体打包好处：

- 后续加字段只需改结构体，函数签名和所有调用方不用动
- 调用时不必死记参数顺序

### 2.3 值传递 vs 指针传递

| 类型 | 推荐方式 | 原因 |
|------|---------|------|
| 简单类型（int, uint8_t, float） | 值传递 | 本身几个字节，效率高且不被意外修改 |
| 结构体、数组 | 指针传递 | 嵌入式栈空间宝贵，避免拷贝浪费 |
| 需要修改原始数据 | 指针传递 | 语义上必须 |

`const` 是契约——告诉调用者"我不会改你的数据"，多人协作时减少沟通成本。

### 2.4 入参校验

- **对外接口函数**：入口处做防御性检查（空指针、越界值），不能省
- **模块内部 static 函数**：如果能确保参数合法，可省掉检查以减少开销

## 3. 返回值设计

### 3.1 必须有返回值的场景

| 场景 | 原因 | 示例 |
|------|------|------|
| 硬件操作 | 硬件从来不是 100% 可靠 | I2C 读写 NACK、Flash 擦写超时、ADC 未完成 |
| 数据解析/协议处理 | CRC 校验、帧长度、命令字都可能异常 | 协议帧解析函数 |
| 资源获取 | 内存分配、队列创建、互斥锁都可能失败 | RTOS API 调用 |

### 3.2 可以用 void 的场景

- 必定成功的简单操作（拉高 GPIO）
- 回调函数（框架/RTOS 要求 void 签名）
- 纯通知/触发类操作（软件复位、喂狗）

判断标准：**这个函数有没有可能失败？失败了调用者需要知道吗？** 两个都回答"否"才用 void。

### 3.3 返回值类型选择

**返回状态/错误码** → 用枚举或整数，项目统一定义错误码：

```c
typedef enum {
    SENSOR_OK = 0,
    SENSOR_ERR_I2C_TIMEOUT = -1,
    SENSOR_ERR_CRC = -2,
    SENSOR_ERR_RANGE = -3,
} Sensor_Status;
```

**返回数据本身** → 把数据通过指针参数带出去，返回值只负责成功/失败：

```c
// ❌ 返回值被正常数据占用，没地方放错误信息
int16_t Sensor_ReadTemp(void);

// ✅ 数据和状态分离
Sensor_Status Sensor_ReadTemp(int16_t *temp);
```

### 3.4 返回值必须检查

非 void 函数的返回值必须被使用（MISRA-C 要求）。确实不需要时用 `(void)` 显式标记：

```c
(void)printf("log: %d\r\n", val);
```

## 4. 好函数的六条标准

### 4.1 单一职责：一个函数只干一件事

判断方法：试着给函数取名字——**如果要用"和"或"并且"才能描述清楚，就需要拆分。**

### 4.2 函数长度：控制在 50 行以内

- 50 行以内是嵌入式的较好范围（IDE 一屏约 40–50 行）
- 超过 80 行就要认真考虑能否拆分
- 协议分发、大量寄存器配置等天然较长的函数例外

### 4.3 命名：让名字替你写注释

| 原则 | ✅ 好 | ❌ 差 |
|------|-------|-------|
| 动词开头 | `Sensor_ReadTemp()` | `temp_data()` |
| 模块前缀 | `Uart_SendFrame()` | `send_frame()` |
| 准确用词 | `Get` = 获取不修改，`Set` = 设置，`Process` = 处理 | 全部用 `Handle()` |

### 4.4 副作用要可控

函数除了计算结果和返回值之外，不应偷偷修改全局状态。如果必须修改，要么在函数名中体现，要么注释说明。最佳做法是把状态管理集中到一个地方。

### 4.5 函数出口尽量统一

推荐"提前返回"模式——开头处理错误情况，末尾统一返回正常结果：

```c
Sensor_Status Sensor_ReadTemp(int16_t *temp)
{
    if (temp == NULL) return SENSOR_ERR_PARAM;

    I2C_Status ret = I2C_Read(DEV_ADDR, REG_TEMP, buf, 2);
    if (ret != I2C_OK) return SENSOR_ERR_I2C_TIMEOUT;

    if (!CRC_Check(buf, 2)) return SENSOR_ERR_CRC;

    *temp = (int16_t)((buf[0] << 8) | buf[1]);
    return SENSOR_OK;
}
```

### 4.6 函数层次：上层调用下层，下层不反调上层

```
┌─────────────┐
│   应用层     │  ← SensorTask_Run()
├─────────────┤
│   服务层     │  ← Sensor_Read(), Protocol_BuildFrame()
├─────────────┤
│   驱动层     │  ← I2C_Read(), GPIO_Set()
└─────────────┘
```

如果下层需要通知上层，用**回调函数或事件机制**，而不是在驱动层直接 `#include "app.h"`。

## 5. 嵌入式环境特殊考量

### 5.1 栈空间

MCU 栈空间有限（Cortex-M0 可能只有 1–2 KB），大数组局部定义会撑爆栈。

应对措施：
- 局部大数组改用 `static` 或全局变量（注意可重入性）
- 大块数据通过指针传入，不在栈上拷贝
- 减少调用层级，避免递归
- 开发阶段用 Keil Call Graph 等工具检测最大栈深度

### 5.2 中断上下文

ISR 限制：执行时间短、不阻塞、不调用不可重入函数、RTOS 环境只能调用 `FromISR` 后缀 API。

设计原则：**中断里只做最少的事情，把复杂处理留给主循环。**

### 5.3 可重入性

如果函数正在执行时被中断打断，中断里又调用了同一个函数，且函数使用了 `static` 局部变量或全局变量，数据就会被覆盖。

可重入条件：
- 避免使用 `static` 和全局变量（或用锁保护）
- 所有数据通过参数传入传出
- 不调用其他不可重入的函数

## 6. 实战重构案例

### 6.1 原始代码问题

一个读取温湿度传感器并上报的函数：

| 问题 | 表现 |
|------|------|
| 职责不清 | 读传感器、校验数据、拆解数据、组帧发送全在一个函数 |
| 全局变量泛滥 | 5 个全局变量（g_sensor_buf, g_send_buf, g_temp_h 等） |
| 没有返回值 | I2C 失败/校验失败上层完全不知道 |
| 不可复用 | 换传感器或协议要推倒重来 |

### 6.2 重构后

| 函数 | 职责 |
|------|------|
| `Sensor_Read()` | 只管读传感器，换传感器只改这一个 |
| `Protocol_BuildSensorReport()` | 只管组帧，换协议只改这一个 |
| `SensorTask_Run()` | 只管编排调用顺序和处理错误 |

全局变量全部消除，数据通过参数在函数间流动，每一步都有错误检查。

## 7. 函数设计自检清单

写完一个函数后快速过一遍：

- [ ] 入参个数 ≤ 3？是否该用结构体打包？
- [ ] 入参用了 `const` 保护只读数据？
- [ ] 对外接口做了空指针/越界检查？
- [ ] 返回值明确（成功/失败），没有用 void 隐藏错误？
- [ ] 非 void 函数的返回值在调用处都被检查了？
- [ ] 函数只做一件事？名字能准确描述？
- [ ] 长度 ≤ 50 行？
- [ ] 没有偷偷修改全局状态？
- [ ] 不会被中断和主循环同时调用（可重入安全）？
- [ ] 局部没有大数组撑爆栈？
