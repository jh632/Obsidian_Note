# 编译链接与内存布局

> 来源：[一文吃透嵌入式编译链接全过程：彻底弄懂内存段布局与分区原理](https://mp.weixin.qq.com/s/7RwkZ44t-1j-5389aTm5PQ) — 嵌入式精进之路 / nezha

## 概述

嵌入式 C 源码到芯片可执行程序，需经过 **预处理 → 编译 → 汇编 → 链接** 四步流水线。链接阶段按数据属性将程序划分为 `.text`、`.rodata`、`.data`、`.bss` 四大逻辑段，再通过链接脚本（`.ld`）将其映射到硬件 Flash/RAM 的物理地址。掌握这套规则是排查 HardFault、内存溢出、OTA 固件异常等问题的底层能力。

## 编译四阶段

| 阶段  | 输入 → 输出       | 核心工作                                       | 关键特性             |
| --- | ------------- | ------------------------------------------ | ---------------- |
| 预处理 | `.c` → `.i`   | 删注释、展开 `#include`、替换 `#define`、处理 `#ifdef` | 纯文本操作，不检查语法      |
| 编译  | `.i` → `.s`   | C 转汇编，**唯一语法校验阶段**                         | 优化级别（O0-O3）在此生效  |
| 汇编  | `.s` → `.o`   | 汇编转二进制机器码                                  | 地址为临时相对地址，不可单独运行 |
| 链接  | `.o` → `.elf` | 合并文件、地址重定位、修复符号引用                          | 生成最终可执行程序        |

## 四大内存段

| 段         | 存储介质        | 占 Flash | 占 RAM | 内容                 |
| --------- | ----------- | ------- | ----- | ------------------ |
| `.text`   | Flash       | 是       | 否     | 函数代码（main、delay 等） |
| `.rodata` | Flash       | 是       | 否     | `const` 常量、字符串常量   |
| `.data`   | Flash + RAM | 是       | 是     | 已初始化的全局/静态变量       |
| `.bss`    | RAM         | 否       | 是     | 未初始化的全局/静态变量       |

- Flash 是**永久仓库**，代码和常量存在这里
- RAM 是**临时工作台**，运行时的变量在这里操作
- `.bss` 不占 Flash → 超大全局数组不会增大固件体积，但会耗尽 RAM

## 栈、堆与四大段的关系

**栈（Stack）和堆（Heap）不属于任何编译逻辑段！** 它们是运行时动态内存区域：

- **栈**：局部变量、函数参数、返回地址。从高地址向下生长，自动分配释放
- **堆**：`malloc` 动态内存。从低地址向上生长，手动分配释放

> 栈和堆相向生长，中间空闲耗尽后二者重叠 → 程序崩溃死机

## 链接脚本（.ld）

链接脚本是嵌入式软件的"城市规划总图"，做三件事：

### 1. 定义硬件内存边界

```
MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}
```

### 2. 绑定逻辑段与物理内存

```
SECTIONS
{
  .text :   { *(.text) }   > FLASH     /* 代码段存入 Flash */
  .rodata : { *(.rodata) } > FLASH     /* 常量段存入 Flash */
  .data :   { *(.data) }   > RAM AT > FLASH  /* 运行在 RAM，初始值保存于 Flash */
  .bss :    { *(.bss) }    > RAM       /* 仅 RAM，不占 Flash */
}
```

### 3. 指定程序入口

```
ENTRY(Reset_Handler)
```

### Boot + APP 双分区

OTA 升级的核心就是修改链接脚本，重新划分 Flash 区域：

```
MEMORY
{
  BOOT_FLASH (rx) : ORIGIN = 0x08000000, LENGTH = 32K    /* Boot 分区 */
  APP_FLASH (rx)  : ORIGIN = 0x08008000, LENGTH = 480K   /* APP 分区 */
  RAM (rwx)       : ORIGIN = 0x20000000, LENGTH = 128K
}
```

## ESP32 编译链接特性（扩展）

ESP32 基于 Xtensa（LX6/LX7）或 RISC-V 架构，编译链接机制与 STM32（ARM Cortex-M）有显著差异：

### 工具链与构建系统

| 项目 | STM32 | ESP32 |
|---|---|---|
| 编译器 | `arm-none-eabi-gcc` | `xtensa-esp32-elf-gcc` / `riscv32-esp-elf-gcc` |
| 构建系统 | Makefile / CubeIDE | **CMake + ESP-IDF**（组件化管理） |
| 链接脚本 | 手动编写单个 `.ld` 文件 | **LF 片段文件（`.lf`）+ `ldgen` 自动生成** |

### 内存架构差异

ESP32 有**独立的指令和数据总线**（类哈佛架构），STM32 的内核 SRAM 是统一编址的冯诺依曼式：

| 区域       | ESP32 地址                      | 用途                   |
| -------- | ----------------------------- | -------------------- |
| IRAM     | `0x4008_0000` - `0x400A_0000` | 可执行代码（需在 RAM 中运行的函数） |
| DRAM     | `0x3FFB_0000` - `0x4000_0000` | `.data`、`.bss`、堆     |
| IROM     | Flash（通过 MMU 缓存映射）            | 大部分代码（默认位置）          |
| DROM     | Flash（通过 MMU 缓存映射）            | `.rodata` 常量（默认位置）   |
| RTC Slow | `0x5000_0000`                 | 深度睡眠保留数据             |
| RTC FAST | `0x400C_0000`                 | 深度睡眠唤醒代码             |

### ESP-IDF 的 LF 片段机制

ESP-IDF 不直接编辑 `.ld` 文件，而是为每个组件编写 **链接器片段（`.lf`）**，系统自动组合生成最终链接脚本：

**内置方案（Schemes）：**
- `default` — 代码放 IROM（Flash），常量放 DROM（Flash）
- `noflash` — 代码强制放 IRAM，常量放 DRAM
- `rtc` — 放入 RTC 内存，用于深度睡眠唤醒

**三种粒度控制：**
- **归档级** — 整个 `.a` 库：`* (noflash)`
- **目标文件级** — 特定 `.o`：`driver/i2c.o (noflash)`
- **符号级** — 特定函数/变量：`driver/i2c.o:i2c_isr_handler (noflash)`

**条件放置：** 支持 Kconfig 条件表达式：
```
if PERFORMANCE_MODE = y:
    * (noflash)
else:
    * (default)
```

### 关键属性宏

ESP-IDF 提供一系列宏，**不需改链接脚本**即可控制符号的放置位置：

| 宏                 | 作用                   | 等价于放入            |
| ----------------- | -------------------- | ---------------- |
| `IRAM_ATTR`       | 函数放入 IRAM            | `noflash` scheme |
| `DRAM_ATTR`       | 常量从 Flash 强制搬入 DRAM  | `dram0_data`     |
| `DMA_ATTR`        | 变量放入 DRAM + 字对齐      | DRAM + 对齐        |
| `RTC_NOINIT_ATTR` | 深度睡眠后保留值             | RTC Slow         |
| `DRAM_STR()`      | IRAM 函数内的字符串也放入 DRAM | —                |

> **IRAM_ATTR 陷阱：** 标记为 `IRAM_ATTR` 的函数内部使用字符串常量时，需同时用 `DRAM_STR()` 标记，否则字符串仍在 Flash（DROM），中断上下文中访问 Flash 会触发 cache miss 导致崩溃。

### ESP32 vs STM32 关键差异总结

| 维度 | STM32 (ARM Cortex-M) | ESP32 (Xtensa/RISC-V) |
|---|---|---|
| Flash 代码执行 | 直接执行（ART 加速器 / 预取缓冲） | 通过 MMU 缓存映射（IROM/DROM） |
| 内存总线 | 统一编址（冯诺依曼风格） | 指令/数据分离（类哈佛） |
| `.data` 搬运 | 启动文件中的循环拷贝 | 启动文件中的 `_data_start`/`_data_end` 循环 |
| 链接脚本 | 单文件手动管理 | LF 片段 + ldgen 自动生成 |
| 堆限制 | 可占用全部剩余 RAM | 320KB DRAM 中最多 160KB 静态分配，其余堆 |
| 中断处理 | 可直接在 Flash 中执行 | 中断需 `IRAM_ATTR` 放入 IRAM |
| DMA 缓冲 | 任意 RAM 区域（对齐要求较低） | 必须 DRAM、字对齐、`DMA_ATTR` 标记 |
| 深度睡眠 | 备份 SRAM（2-4 KB） | RTC Slow + RTC FAST 内存（8 KB + 8 KB） |

## 上电启动流程

```
芯片上电 → CPU 读 Flash 入口 → 执行 Reset_Handler
  → 搬运 .data 段（Flash → RAM）
  → 清零 .bss 段
  → 初始化栈、堆
  → 跳转 main()
```

## ELF 文件结构

- **`.o`** = 书的单页（有内容，没页码）
- **ELF** = 装订好的书（有目录、页码、索引）
- **`.bin`** = 撕掉封皮，只留正文
- **`.hex`** = 每页贴了快递单（地址）的书页

ELF 文件包含 ELF 头、程序头表（加载视图）、节头表（链接视图）、符号表。调试器通过符号表定位函数/变量地址。

## BIN vs HEX

| 特性 | BIN | HEX |
|---|---|---|
| 格式 | 纯二进制 | 文本（带地址+校验） |
| 体积 | 最小 | 较大 |
| 适用 | OTA、串口 IAP、量产 | 开发调试、离线烧录 |

> BIN 文件可能有"空洞"（地址间隙用 0 填充），OTA 传输时需考虑这部分额外开销。

## 高频踩坑

1. **全局大数组 RAM 溢出** — `.bss` 不占 Flash 但耗 RAM，改用 `const` / `malloc` / 外部存储
2. **修改字符串常量 HardFault** — 字符串在 `.rodata` 只读区域，用 `char arr[]` 代替 `char *ptr`
3. **`.data` 段过多耗尽双内存** — 无需初值的大缓冲区不用初始化、固定参数用 `const`
4. **局部大变量 / 递归栈溢出** — 避免局部大数组、控制递归深度
5. **`malloc` 未释放 / 碎片** — 使用 goto cleanup 模式或实现内存池
