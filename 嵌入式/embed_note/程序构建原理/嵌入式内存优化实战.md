# 嵌入式内存优化实战

> 来源：[RAM爆了，FLASH也满了？聊聊嵌入式开发中真正管用的内存优化手段](https://mp.weixin.qq.com/s/DywLxL_VgRBkzwhw5_6I9g) — 一枚嵌入式码农

## 概述

编译报错 `region 'RAM' overflowed by 1024 bytes` / `region 'FLASH' overflowed by 2376 bytes` 是嵌入式开发的常见窘境。换大芯片要重新打板认证、砍功能产品经理不同意，只能走第三条路：在现有资源里优化。本文按实际优化的工作顺序展开：**先搞清内存去哪了 → FLASH 怎么省 → RAM 怎么省 → 变成日常习惯**。

## 一、优化之前，先搞清楚代码和数据都放在哪

一个典型 MCU 程序编译链接后分这几个段：

| 段         | 存储介质        | 内容                                       |
| --------- | ----------- | ---------------------------------------- |
| `.text`   | FLASH       | 代码段，C 代码编译成的机器指令                         |
| `.rodata` | FLASH       | 只读数据段，`const` 常量、字符串字面量                  |
| `.data`   | FLASH + RAM | 已初始化的全局/静态变量，初值存 FLASH，运行时空 FLASH 搬到 RAM |
| `.bss`    | RAM         | 未初始化（或初始化为 0）的全局/静态变量，启动时统一清零            |

加上运行时的**堆**和**栈**，RAM 的账就齐了。

两个实用结论：

1. **FLASH 占用 = .text + .rodata + .data 初值** → 从代码量、常量数据、库函数方向下手
2. **RAM 占用 = .data + .bss + 堆 + 栈** → 从全局变量、缓冲区、堆栈配置方向下手

## 二、动手改代码之前，先找到真正的大户

优化内存和优化性能一样：**不要凭感觉，要看数据**。

### 2.1 size 命令看总账

GCC 工具链编译完成后跑 `size`（或 `arm-none-eabi-size`），一眼看出大头在哪：

- `.bss` 大 → RAM 压力来自全局缓冲区，而不是堆栈
- `.text` 大 → 代码本身才是 FLASH 的大户

### 2.2 map 文件精确到人

链接器生成的 map 文件（Keil 是 `.map`，GCC 加 `-Wl,-Map=output.map`）列出每个函数、每个变量的字节数和地址。直接搜 `.bss` 段按大小排，经常能看到：一个日志缓冲区 8KB + 一个串口接收缓冲区 4KB，在 32KB RAM 的芯片上直接吃掉三分之一。

Keil 用户看 Build Output 里的链接统计或 map 文件末尾的 **Image component sizes**，按模块（.o 文件）汇总 Code、RO-data、RW-data、ZI-data 四项。

### 2.3 给自己定个规矩

优化前把 size 输出和 map 文件里**排前十的函数、变量抄下来**，优化一轮后对比，每个改动省多少字节心里有数。前三名的大户处理完往往就解决了一大半问题。

## 三、FLASH 优化：让代码段瘦下来

FLASH 优化收益通常比 RAM 快，因为很多手段是编译选项层面的，不用大改代码。按"先易后难、先收益大后收益小"的顺序：

### 3.1 把优化等级调对

- GCC / Keil AC6：`-Os`（更激进用 `-Oz`）
- 还在用 `-O0` 调试配置直接出货的，换 `-Os` 可能省出 **30% 以上**代码空间
- `-Os` 本质是在 `-O2` 基础上关掉"用空间换时间"的优化（激进循环展开、函数内联）

> ⚠️ 优化等级上去后，写得不规范的代码会露馅：该加 `volatile` 没加的变量被优化掉，导致中断标志位死等。换了优化等级程序跑飞，先别怪编译器，大概率是代码本身有问题。

### 3.2 让链接器把没用到的代码扔掉

默认链接器以 .o 文件为单位：一个文件里任何一个函数被用到，整个文件都会被链进来。

```
编译选项: -ffunction-sections -fdata-sections
链接选项: -Wl,--gc-sections
```

前者让每个函数/变量进独立段，后者丢弃没被引用的段。Keil 对应 **One ELF Section per Function** 选项，默认工程模板一般已开，但手搭的 Makefile 工程经常漏。

### 3.3 链接时优化 LTO

`-flto` 让编译器在链接阶段拿到全局视野，做跨文件内联和死代码消除，通常再省 **5%~10%**。代价：链接变慢、调试信息不好对应。**只在发布配置开，调试配置保持关闭**。

### 3.4 printf 是个无底洞

标准库 printf 为支持完整格式化（尤其浮点）会拖进一大串依赖。Cortex-M0 这类无硬件浮点的核上，一个 `%f` 可能让代码体积暴涨 **10KB 以上**。对策分层次：

1. GCC 加 `--specs=nano.specs` 换 newlib-nano，浮点默认关闭，需要时 `-u _printf_float` 显式打开
2. Keil 勾选 **Use MicroLIB**
3. 只打日志就换开源轻量实现：mpaland 的 printf、tiny printf（几百行代码）
4. 日志格式里能不用 `%f` 就不用，用**整数放大**方式绕过去（如 `value * 100` 输出两位小数）

### 3.5 留意隐式拖进来的库函数

- 无硬件除法器的核（Cortex-M0/M0+）上，整数除法/取模会引入**软件除法库**
- `double` 运算会拖进**软浮点库**
- `memcpy`、`memset` 在不同优化等级下实现大小不同

在 map 文件里搜 `__aeabi_` 开头的符号看它们占多少。对策：除以 2 的幂用移位；double 常量写 `1.5f` 而不是 `1.5`，避免整个表达式被提升成 double 运算。

### 3.6 数据也能省：查表和资源的取舍

- **用计算换存储**：1024 点正弦表占 2KB/4KB，调用频率不高就运行时计算，或利用对称性只存 1/4 周期，缩水到原来的四分之一
- **资源压缩或外置**：中文字库按需裁剪只提取用到的字；大资源放外部 SPI Flash，用文件系统或分区表管理
- **去掉调试期字符串**：`assert` 宏会把文件名、行号字符串编进 `.rodata`，发布版本用 `NDEBUG` 关掉，或重定义成只记录错误码的轻量版本

## 四、RAM 优化：每个字节都要花在刀刃上

RAM 通常比 FLASH 更金贵（FLASH 128KB 配 RAM 20KB 是常态）。从 .data、.bss、堆、栈四个方向下手：

### 4.1 该 const 的一定要 const（性价比最高）

忘了加 `const` 的只读数据会放进 `.data`，白白占一份 RAM。一个 256 项的 CRC 表就是 512 字节。检查方法：在 map 文件里过一遍 `.data` 段，凡运行期间从不写的都加上 `const`。

### 4.2 给全局变量和结构体瘦身

**数据类型**：状态标志用 `int` 就是拿 4 字节干 1 字节的活，用 `uint8_t`、`int16_t` 等定宽类型。单个变量不起眼，乘上数组长度就可观：500 个节点的数组，每个省 4 字节就是 2KB。

**结构体对齐**：编译器按成员对齐要求插入填充字节。成员按**从大到小排列**填充最少。要开成大数组的结构体（协议缓存池、链表节点池），调整成员顺序能省百分之几十。布尔标志多用**位域**，8 个标志压进 1 个字节。

> ⚠️ 不建议无脑用 `#pragma pack(1)` 全局压缩对齐：非对齐访问在有些内核上硬件异常，另一些内核上悄悄变慢。手动排列成员顺序更稳妥。

### 4.3 大缓冲区：复用与按需分配

- **互斥缓冲区合并**：OTA 接收缓冲区和正常运行时的日志缓冲区业务上不会同时工作，用 `union` 共用一块内存，省一半。**要配注释说明互斥条件**，否则接手的人踩坑
- **内存池**：几种固定大小的块，按需申请、用完归还，避免 malloc 碎片，峰值内存可控
- **审视 buffer 尺寸**：串口接收缓冲开 4KB、实际协议最大帧长 200 字节的情况太常见。按协议真实最大帧长 + 合理余量定，别用"开大点保险"的思路

### 4.4 堆：能不用就不用

小 RAM 项目尽量不用 `malloc`，三个原因：

1. 堆本身要预留不小的空间
2. 反复申请释放产生碎片，跑几个月后总剩余够却分配不出连续内存
3. 分配失败的处理路径很少有人认真写

替代方案：静态分配 + 内存池。确实要用堆（第三方库内部用了 malloc），堆大小压到实测峰值 + 余量，测试阶段监控堆高水位。

### 4.5 栈：别再拍脑袋给 1KB

栈给小了，溢出把相邻内存改得面目全非；给大了纯粹浪费。两个实用做法：

1. **编译期估算**：GCC 加 `-fstack-usage` 为每个函数生成 `.su` 文件列出栈消耗，结合调用关系算最深路径。Keil 的 map 文件里有 **Maximum Stack Usage** 静态分析结果
2. **运行期实测（水位法）**：启动时把栈空间填成固定魔术字，跑完典型业务场景后看魔术字从哪里被破坏。RTOS 用现成接口：FreeRTOS 的 `uxTaskGetStackHighWaterMark()`

我的习惯：按实测水位再留 **30% 左右**余量，中断嵌套深、递归多的场景适当放宽。

**两条相关代码习惯**：
- 函数内部不要开大的局部数组，`char buf[1024]` 就能把小任务栈干穿，大缓冲区静态分配或走内存池
- 坚决不写递归，任何递归都可以改写成循环 + 显式栈

## 五、把优化变成习惯，而不是救火

1. **每次编译都盯着资源占用**：把 `size` 命令挂到编译脚本最后一步，每次构建输出四个段的大小；更进一步在 CI 加规则，FLASH/RAM 占用超阈值就告警
2. **给项目定资源红线**：量产版本 FLASH 不超过 85%、RAM 静态占用不超过 80%，给 bugfix、新需求、OTA 升级留余地
3. **优化记录留档**：每项优化记下改了什么、省了多少、有什么副作用，下个项目选型时是最真实的依据
4. **顺序很重要，先测量再动手**：最亏的是花三天抠出 200 字节，回头发现一个忘加 const 的表占 2KB。map 文件先看，大户先抓

## 六、写在最后

内存优化考验的是对程序的了解程度：每一 KB 花在哪里、为什么花、值不值。往深了想，内存紧张很多时候只是表象——模块划分混乱、协议与业务耦合反复拷贝、全局变量满天飞，这些**架构层面的问题才是资源浪费的根源**。优化技巧能救一时，清晰的架构才能让项目长期健康。

## 高频要点速查

- FLASH = .text + .rodata + .data 初值；RAM = .data + .bss + 堆 + 栈
- 先 size 看总账、map 文件排前十，再动手
- FLASH：`-Os` → `-ffunction-sections -fdata-sections` + `--gc-sections` → `-flto` → printf 瘦身 → 查库函数 → 查表数据
- RAM：`const` → 数据类型/结构体对齐 → 缓冲区 union 复用/内存池 → 少用堆 → 栈实测 + 30% 余量
- 资源红线：FLASH ≤ 85%，RAM ≤ 80%
