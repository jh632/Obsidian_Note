## 1. 继承：C 的嵌套 struct 变成语法

### 1.1 回顾：C 里的"继承"长什么样

LVGL 类型树：`lv_button_t` 首成员就是 `lv_obj_t` → button "is-a" object。
C 里继承 = **手工嵌套 struct + 手工访问基类字段**，is-a 关系靠纪律维持；C++ 把这条纪律变成语法。

### 1.2 语法

```cpp
class Sensor {                // 基类：公共部分
public:
    explicit Sensor(uint8_t addr);
    esp_err_t read();
protected:
    uint8_t addr_;            // ★ protected：子类能用，外部不能
};

class GH3220 : public Sensor {    // ★ 继承语法：类名 : public 基类名
public:
    explicit GH3220(uint8_t addr);
    float read_temp();            // 自己的新能力
};
```

- `: public Sensor` = 公开继承，表达 **is-a**（GH3220 是一个 Sensor），适合对外提供统一的传感器接口
- 继承 = **复用基类的成员函数 + 加自己的新成员**，不是复制代码

### 1.3 protected：权限表补完

| 权限 | 类自己 | 子类 | 外部 |
|---|---|---|---|
| private | ✅ | ❌ | ❌ |
| protected | ✅ | ✅ | ❌ |
| public | ✅ | ✅ | ✅ |

基类里"给子类用的工具"（如 `addr_`）放 protected；对外接口放 public；内部细节放 private。

### 1.4 构造/析构顺序（编译器保证）

- 构造：**先基类后派生**（基类是地基）
- 析构：**先派生后基类**（先拆自己的，再还地基）

基类没有默认构造时，派生类必须在初始化列表里显式调用：

```cpp
GH3220::GH3220(uint8_t addr) : Sensor(addr) {}   // 先构造 Sensor 部分
```

### 1.5 内存布局：包含基类子对象

GH3220 对象包含 Sensor 基类子对象和自己的成员，可以借助 C 的嵌套 struct 理解“包含基类部分”。但 C++ 不保证基类总在对象开头，也不保证布局与 C 完全相同；虚函数、多重继承和对齐等会影响实际布局。

### 1.6 继承后，子类必须实现什么

**继承本身不要求子类重新实现父类的所有函数。** 是否必须实现，主要看有没有纯虚函数，以及是否要创建子类对象。

| 父类中的内容 | 子类的规则 |
|---|---|
| 普通成员函数 | 不必重新实现，可以按访问权限使用；同名函数不会自动获得虚调用能力 |
| 有实现的虚函数 `virtual` | 可以沿用父类实现，也可以重写 |
| 纯虚函数 `virtual ... = 0` | 想创建子类对象，必须补齐仍未实现的纯虚接口；否则子类仍是抽象类 |
| 构造函数 | 必须先正确构造父类；没有可用的默认构造函数时，在初始化列表中给父类传参 |
| 虚析构函数 | 子类析构自动为虚函数；没有额外清理工作时，不必手写子类析构 |

“补齐纯虚接口”不要求每层子类重复写实现：如果中间父类已经提供了非纯的重写，后续子类可以直接继承该实现。抽象类可以继续作为基类，也可以声明其指针或引用，但不能直接创建它的对象。

下面是一个独立的完整示例，使用普通 C++ 类型展示规则：

```cpp
class Sensor {
public:
    explicit Sensor(int addr) : addr_(addr) {}
    virtual ~Sensor() = default;

    int address() const { return addr_; }  // 普通函数：直接复用
    virtual bool init() { return true; }  // 虚函数：可选择重写
    virtual int read() = 0;               // 纯虚函数：规定读取接口

private:
    int addr_;
};

class GH3220 : public Sensor {
public:
    explicit GH3220(int addr)
        : Sensor(addr) {}                 // 先初始化父类部分

    int read() override {                 // 补齐纯虚接口
        return 123;                       // 示例值，实际应读取硬件
    }
};

int main() {
    GH3220 gh(0x34);
    gh.address();                         // 使用父类普通成员函数
    gh.init();                            // 使用父类默认实现

    Sensor& s = gh;                        // 公开、无歧义的继承允许向上转换
    s.read();                             // 虚调用：执行 GH3220::read()

    Sensor* p = new GH3220(0x34);
    delete p;                             // 虚析构：正确销毁整个派生类对象
}
```

如果删除 `GH3220::read()`，`GH3220` 仍是抽象类，`GH3220 gh(0x34);` 和 `new GH3220(0x34)` 都不能编译。这里不需要重写 `init()`，也不需要手写 `~GH3220()`。

### 1.7 重写规则：使用 override 帮编译器检查

- 父类函数必须是虚函数，才能在子类中重写；父类已声明 `virtual` 后，子类不必重复写 `virtual`。
- 重写时函数名、参数列表以及成员函数的 `const`、引用限定等必须匹配；返回类型通常相同（协变返回是例外）。
- 在子类写 `override`：签名写错时编译器直接报错，避免误写成另一个函数。
- 普通成员函数不会仅因为子类定义了同名函数就产生多态；同名声明还可能隐藏父类的其他重载。
- 父类虚函数标记 `final` 后不能再重写；类标记 `final` 后不能再被继承。

```cpp
class Base {
public:
    virtual int read() const { return 0; }
};

class Derived : public Base {
public:
    // int read() override { return 1; }  // 错误：缺少 const，没有重写父类函数
    int read() const override { return 1; }
};
```

### 1.8 继承方式与成员权限

成员的 `public` / `protected` / `private` 与继承方式是两层规则：

| 父类成员原权限 | public 继承后 | protected 继承后 | private 继承后 |
|---|---|---|---|
| public | public | protected | private |
| protected | protected | protected | private |
| private | 子类不能直接访问 | 子类不能直接访问 | 子类不能直接访问 |

父类的私有数据仍然存在于基类子对象中，只是子类不能直接访问；可以通过父类提供的可访问成员函数间接操作。上例中 `GH3220` 不能直接访问 `addr_`，但可以调用 `address()`。

`class GH3220 : Sensor` 默认是 **private 继承**；`struct GH3220 : Sensor` 默认是 **public 继承**。表示对外的 is-a 关系时明确写 `public`，避免依赖默认值。

外部代码通常通过公开且无歧义的继承，把派生类指针或引用转换为基类指针或引用。`protected` / `private` 继承会限制这种转换的访问范围。

> `namespace drivers { class Sensor; }` 只组织名字，不产生继承。建立父子类关系要写 `class GH3220 : public Sensor`。

## 2. 虚析构：为什么基类析构要加 virtual

### 2.1 出事的场景

堆上 + 基类指针管理派生类对象（第 3 章多态的引子）：

```cpp
Sensor *s = new GH3220(0x34);
delete s;    // 危险！
```

在这里通过基类指针进行普通 `delete`，如果 `Sensor` 没有虚析构函数，就是**未定义行为**。不能把它理解成“保证只调用 `~Sensor()`”；漏掉派生类资源清理只是可能出现的后果之一。

### 2.2 解决：基类析构加 virtual

```cpp
class Sensor {
public:
    virtual ~Sensor() {}   // ★ 关键一行
};
```

- delete 时走**虚表**，运行期找到真实类型 GH3220 → 先 `~GH3220()` 再 `~Sensor()`（顺序又对了）
- 派生类析构自动是 virtual，不用每个都写

### 2.3 什么时候必须加 / 不用加

| 场景 | 基类析构 |
|---|---|
| 需要通过基类指针执行普通 `delete` 删除派生类对象 | **必须 virtual** |
| 对象全在栈上（嵌入式默认） | 可以不加——栈对象离开作用域，编译器**静态调用**正确析构，不需要虚表 |

仅仅用基类指针或引用访问对象，并不必然要求虚析构；关键是是否允许通过基类指针删除对象。设计允许这种删除方式的多态接口时，使用公开的虚析构函数，即使没有清理代码也可以写 `virtual ~Sensor() = default;`。

### 2.4 成本（嵌入式注意）

常见实现使用对象中的 **vptr（虚表指针）** 和按类型共享的虚表。简单继承下，32 位平台的 vptr 通常为 4 字节，64 位平台通常为 8 字节；实际对象大小还受对齐和继承结构影响，不是标准规定的固定开销。

如果类已经有其他虚函数，增加虚析构通常不再增加一个对象内指针，但会影响虚表和相关代码。虚调用还可能涉及间接调用成本；具体布局、存储位置和优化效果取决于编译器、ABI 与构建配置。

三/五法则引子：是否需要禁止拷贝或实现深拷贝，取决于类是否拥有资源，不能仅凭“有虚析构”判断。多态基类还应考虑避免按值拷贝引起的对象切片。

## 3. 语法映射总表

| C（你的写法） | C++ | 约束 |
|---|---|---|
| `struct GH3220 { Sensor base; ... }` + 手工访问 base 字段 | `class GH3220 : public Sensor` | 编译器保证 is-a |
| 注释"子类才能动这些" | `protected:` | 编译器强制 |
| 手工保证"先初始化基类" | 构造函数顺序 | 编译器保证 |
| 基类指针 delete 派生类对象（漏析构） | `virtual ~Sensor()` | 运行期查真实类型 |

## 4. 嵌入式实战要点

1. **组合优先于继承**：Device 组合类（has-a）继续用；继承用在"真的是同一族"（is-a）。GH3220/MPU6050 都是传感器 → 可以继承 Sensor；Device 里装多个传感器 → 组合
2. **别为"未来可能"提前继承**：只有一个传感器型号时，直接写 GH3220 类就行（YAGNI，和 GpioPin 删死配置一个思路）
3. **构造不碰硬件的约定在继承下不变**：派生类构造函数只存参数（先调基类构造），init() 才碰硬件——派生类的 init() 可以先调基类的 init() 再初始化自己的部分

## 5. 一句话总结

**继承 = C 嵌套 struct 的语法化 + 访问控制；虚析构 = 让"基类指针 delete 派生类对象"时，析构链按 派生→基类 完整执行的那一个 virtual。**
